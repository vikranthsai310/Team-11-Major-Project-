Batching swaps on Cardano — deciding when and how many

A decentralized exchange keeps each liquidity pool in a single UTXO that only one transaction can spend per block. A batcher collects many users’ orders and settles them together. This project decides, block by block, whether to wait or to submit — and proves the decision on real chain data.

1

Users place orders; the batcher settles them together

A user locks funds at the order contract with their terms: how much to sell and the minimum they will accept. They never talk to the batcher — it finds orders on chain.

2

The pool lock: one batch at a time

A submitted batch spends the pool and recreates it. Until it confirms, no second batch can be built — every new order waits behind it. That head-of-line blocking is the real cost of a badly timed submission.

3

Cardano fees don’t rise with demand — so time is the cost

Cardano’s fee is a fixed formula of size and script cost. There is no gas auction. Waiting never makes a transaction cheaper, so the goal is lower latency and lower cost per user — not “lower gas fees”.

fee = 44 × size + 155,381 + 0.0577 × memory + 0.0000721 × steps lovelace

Batching still saves money: the flat part of the fee is shared by everyone in the batch. Our contract passes that saving to users — each pays network fee ÷ n + margin.

4

Two different limits — Gate A and Gate B

Gate A · per transaction

How big a batch can ever be (16,384 bytes, 14 M memory). Always binding. An empty block does not allow a bigger batch. Breaking it is a bug — it never happened in any run.

Gate B · per block

Whether the batch fits the block being produced. Depends on how full the chain is. Failing it only means waiting for the next block, never rejection.

5

What we measured first changed the project

We collected 388,781 real mainnet blocks over 92 days. The usual claim was that blocks run 80–90 % full. They don’t: the median block is 2.95 % full and only 0.56 % exceed 80 %. So the real problem is the pool lock, not congestion — and the project was reframed around it.

6

The decision-makers we compared

  • E1 / E2 / E3 — today’s fixed rules: wait for 16 orders, submit every 20 s, or submit immediately (greedy).
  • P1 — a LightGBM model forecasting how full the next blocks will be.
  • P2 — an explainable optimizer: submit now unless a quieter block is coming and the batch is still small.
  • P3 — a Deep Q-Network agent that learned when to submit, with illegal actions masked.
7

The honest result

On 100 held-out test days, no policy beat greedy on speed — when blocks are nearly empty, submitting immediately is already fastest. The adaptive policies instead give a controllable trade-off: P2 cuts cost per user by 19 % for 5 % more tail latency, and stays robust when traffic doubles while the fixed rules break down. Zero capacity violations across every run.

8

And it runs on a real blockchain

Our own DEX is deployed on Cardano’s preprod test network. A real order was placed and the live batcher settled it: the user received 90,661 TEAM11, and the contract enforced their minimum and fee share.
